# 架构决策记录(ADR)

> 每条记录:背景 → 决定 → 后果 → 被否决的替代方案。
> 目的是让后来者(包括未来的 agent)知道"为什么是这样",避免把已经想过的问题重新推翻一遍。

---

## ADR-0001 存储用纯 Markdown 文件 + 派生视图

**背景**:记忆需要被 DSH / Octop / Pi / 未来的 harness 共同读写,而它们唯一稳定共有的能力是"读写文件"和"跑 shell"。

**决定**:真相是不可变的 `atoms/<yyyymm>/<id>.md`;`views/`、`index/` 全部是派生品,可随时重建。

**后果**:并发写零冲突(不同文件);单条可追溯、可回滚;合并逻辑可测试。代价是文件数变多,所以检索必须走服务端而不是挂载扫描。

**否决**:直接用主题文件当真相 —— 无法表达"哪条取代哪条",也无法单条回滚。

## ADR-0002 传输用单个 HTTP 入口,而不是 SMB 挂载或 git

**背景**:端经 EasyTier 接入,实测笔记本→边缘网关 P2P 8.8ms、边缘网关→服务器 0.3ms。

**决定**:端只调 `POST/GET /v1/*`,由服务器上的 `brain serve` 统一处理。

**后果**:一次 `brief` 是一个请求一个响应包,而不是几十次小文件往返;笔记本重启不掉挂载;手机端零成本;身份可在服务端签发。

**否决**:SMB 挂载(小文件往返在 mesh 上会被放大)、git 每端 clone(记忆文件 merge 冲突极难解)。SMB 仅保留为应急只读通道。

## ADR-0003 单写者:只有服务器进程能改数据

**背景**:多端同时写会引出锁、冲突合并、部分写入等一整类问题。

**决定**:端只能"提交一条记录",所有落盘、视图重建、索引更新由服务器上同一个进程完成。

**后果**:不需要分布式锁;只要保证"提交幂等"(见 ADR-0004)就不会丢数据。代价是服务器成为写路径单点 —— 用端侧 outbox 缓解。

---

## ADR-0004 幂等键由客户端生成(UUID),不是服务端生成

**背景**:端可能离线,恢复后要重放;网络抖动可能重复提交。

**决定**:**幂等键只有 `id`**。`id` 在端侧生成;同 id 且全字段一致 → 幂等成功;同 id 但内容不同 → 409,
绝不覆盖不可变文件。`hash` 不参与判重,只用于"同 author + 30 秒窗口"内的疑似重复提示,且提示后
**端侧不删本地条目**。

**后果**:重放天然安全;离线可先落盘再补交;两端各自写下同一事实时**保留两条**,交给冲突视图。

**为什么不能把 hash 当幂等键**(评审 P0):两端离线各写一条相同事实,后到的会被判重返回
`stored:false`,端侧把 outbox 条目当作成功删除 —— 那一端的事实和它的 `supersedes` 边**永久消失**,
而且是静默的。这正是 ADR-0005 最想避免的失败形态。

(本条初稿写的是"id 或 hash 双重去重",那是错的,已更正。)

## ADR-0005 不做冲突的自动合并

**背景**:两条记录对同一事实给出不同结论是常态(环境变了、或其中一条是错的)。

**决定**:视图并列展示 + 标记冲突,由人或 agent 显式裁决,裁决结果写成新记录。

**后果**:永远不会静默丢失一条事实;代价是偶尔需要人工拍板。

**否决**:取最新一条 —— 用户永远不知道另一条被丢了,这是 LLM 记忆系统最常见的翻车点。

## ADR-0006 角色只做"语气/职责"一层

**背景**:使用者明确只需要不同端有不同口吻与职责,不需要可见性隔离或权限系统。

**决定**:`profiles/<role>.md` 决定 persona;所有记忆共享;但每条记录仍保留 `host/harness/role` 三元组。

**后果**:实现成本低;以后若要升级到可见性隔离,历史数据已带齐字段,不需要迁移。

**纪律**:事实必须写成中性句 —— 语气只能存在于 profile 与 journal,否则人格会跨端串味。

## ADR-0007 密钥用 age 多收件人 + `secret exec`,而不是 `secret get`

**背景**:使用者要求"密码可以入库但必须加密"。

**决定**:密文 `secrets/<name>.age` 进 git,各端只持私钥;取用时 `brain secret exec` 把明文注入子进程环境变量,不打印。

**后果**:加密保护了文件、git 历史、磁盘;但**保护不了 agent 的会话日志**,所以"不打印"必须靠 `exec` 这个用法来保证。私钥只能人工分发一次,自动同步密钥等于没有加密。

**吊销不是 O(1)**(评审 P0):age 对每个 recipient 分别加密,删掉一把公钥只影响以后;
旧密文仍可被丢失设备解开。真正吊销 = 轮换底层口令 + 重加密全部 secrets + 视需要 filter-repo。
初稿写的"只吊销公钥、不用重刷"是假的安全保证,已更正。

**否决**:把密文解密后交给模型 —— 明文一旦进入一次工具输出,就被永久写进 transcript。

## ADR-0008 边缘只做"可选前置",`serve` 留在主服务器

**背景**:一个常开的低配设备(aarch64、2 GB 内存、无 python3)与主服务器同在局域网,适合作反向代理层。

**决定**:真相与服务都留在主服务器;只有"需要公网入口 / 固定命名 / 集中限流"时才在前面加一层反代。

**后果**:数据在自己手里,快照与 git 历史都在;反代故障只影响远端入口,不影响局域网内使用。低配设备的存储多是 flash,不适合长期写。

**已被实测推翻的一个假设**:最初以为"端只能单向发起,服务器不能反连端";实际只要两者在同一局域网,服务器可以主动推送副本,所以"边缘只读副本"是可行的。

## ADR-0009 边缘不缓存记忆内容

**背景**:直觉上缓存在边缘能让服务器重启时也能读。

**决定**:边缘只做反代/TLS/限流/日志;端侧可缓存 last-known-good brief,但必须带 `stale` 标记。

**后果**:不会出现"读到过期事实却以为是最新"的情况。记忆读到旧的比读不到更危险,因为旧事实会被当真相复述且不会自我暴露。

## ADR-0010 中文检索必须 bigram 化

**背景**:SQLite FTS5 的 `unicode61` 分词器按空格/标点切词。

**决定**:写入时同时生成 bigram 列;查询也 bigram 化后匹配。

**实测**(服务器,Python 3.11.2 / SQLite 3.40.1):`unicode61` 搜"代理""地址"均为 0 条;bigram 均为 1 条。

**后果**:无需第三方分词依赖;`LIKE` 兜底不需要。

## ADR-0011 路由管理面保留对 mesh 开放(使用者决定)

**背景**:路由的 LuCI(80/443)与 ttyd(7681)都对 mesh 可达;SSH 已改为仅公钥。

**决定**:SSH 关闭口令登录并从地址上绑定 LAN;ttyd 对 mesh 封禁;LuCI 保留开放,root 口令不轮换。

**后果**:mesh 成员(含公司 Win11)仍可打开完整网页管理面,唯一屏障是 root 口令。这是被明确接受的残余风险,不是遗漏。

**回滚**:见 `hosts/edge-gateway.md`。

## ADR-0012 状态变更用追加式 tombstone,atom 永不修改

**背景**:"遗忘"如果写成改 atom 的 `status` 字段,就与 ADR-0001 的不可变性冲突;而且以后无法区分
"写入时就是 deprecated"与"三个月后标记的",git diff 也失去审计意义。

**决定**:`tombstones.jsonl` 追加,`{id, status: deprecated|retracted|active, at, reason, author}`;
atom 一个字节都不动;视图 = atoms ⊕ tombstones。

**后果**:审计完整、可恢复、可回溯;代价是多一个文件和一次过滤。
验收标准:**标记遗忘后 `git status` 里 atom 必须零 diff。**

## ADR-0013 事件时间与入库时间分离

**背景**:端可能离线数天/数月再补交。若只存一个 `ts` 且取入库时间,两个月前的旧事实会排到最前、
拿到最高 recency 权重,agent 会把它当最新复述。

**决定**:`occurred_at`(客户端事件时间,重放时保真)+ `received_at`(服务端权威时间)。
排序与 recency 用前者,冲突裁决与审计用后者;两者差 > 5min 时 `time_suspect: true` 并告警,**不静默改值**。

**后果**:离线历史排序正确;时钟不可信时如实标注。
`ttl` 改为**查询时判定**(`Asia/Shanghai` 当日 23:59:59),而不是每天重建时判定 —— 否则过期事实还能被读最多 24 小时,违反 ADR-0009。

## ADR-0014 不迁移到第三方记忆框架,坚持自建轻量方案

**背景**:2026-10 评估了两个同域产品:

- `Tencent-Hunyuan/Hy-Memory`(双系统认知记忆 2.0 + MemHub,Apache-2.0):L0–L7 分层、L2 事实"版本化不可变"、
  Working/Coding 双层"事实 + 经验"。
- `volcengine/OpenViking`(AGPLv3,context database):`viking://` 虚拟文件系统 + 目录级 L0/L1/L2 sidecar、
  resources/memories/skills 三类、已有官方 DSH 插件(进程内 Cordis 插件 + 事件流捕获 + MCP)。

两者都与 ADR-0001 的判断同源(纯文本/文件系统是各 harness 的唯一交集);OpenViking 更已经在插件层
解决了"自动捕获 + 自动注入"—— 那正是本方案最薄的一环。

**决定**:**不迁移**。真相层继续留在本仓库;第三方只允许以**只读**形态出现在边缘(资料库 / 镜像),
且**永不双写**。

**理由**(按权重):

1. **失败模式**:两者的记忆都是 LLM 抽取的产物 —— 异步、不可 `git diff`、冲突在抽取管线内合并。
   运维事实(IP / 端口 / 版本 / 归属)必须精确且可追责,经过一次抽取即失去"可复核"这一属性。
2. **稳定性**:OpenViking 处于 0.4.x pre-1.0,索引记录格式升级**单向**(降级必须恢复备份);
   且需 uv + Python 3.10+ + embedding + VLM 才能写入,等于把本地记忆的写路径挂到外部模型服务上。
3. **可维修性**:AGPLv3,且明示禁止"整体重写后重新开源"、大规模转译需书面授权 —— 坏了不可修、不可 fork。
   本仓库是自持的,这一条本身属于稳定性。
4. **成本**:迁移的明确收益只有"自动捕获/检索"和"资料 RAG"。前者可在端侧插件补(见待办),
   后者可外挂一个只读实例,都不需要动真相层。

**后果**:继续保留"写入靠 agent 纪律"这一已知短板(与 ADR-0005 同源);需要自己补端侧插件才有
事件流级自动化。代价可控,且数据格式(markdown + frontmatter)**零锁死** —— 任何时点可重新评估。

**否决**:

- 整体迁移到 OpenViking / Hy-Memory —— 事实会被有损压缩,且失去版本控制与离线写。
- 双写(brain 与第三方各写一份)—— 两周内会产生两个互相矛盾、且无法判定新旧的真相源。
- 把数据层改成向量检索 —— 违反 D4(数百条规模);语义召回对精确运维事实是负收益。

**复查触发条件**(任一成立则重开此 ADR):① 第三方出现显式取代/版本语义(而非仅合并);
② 提供 git / 纯文本导出;③ 发布 1.0。

**待办**(不阻塞):① 端侧 client plugin,只做"捕获 → outbox 建议",**不自动改 atom**;
② 若引入资料库,必须独立端口、独立目录,且不装其 DSH 记忆插件。
