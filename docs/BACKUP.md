# 备份与恢复（参考设计）

> 这份文档回答一个问题：**当那台机器上的库、甚至那台机器本身没了，你还能不能在半小时内把记忆恢复回来，并且知道恢复出来的是"对的那一份"。**
>
> 本文是参考设计，不是代码。仓库交付的是库本体（`bin/brain` + `brainlib/`），备份是运维侧的事——
> 你需要按自己的环境写 200 行左右的脚本，本文给的是**每一步的判据和红线**。

---

## 0. 先摆正威胁模型

备份系统的设计完全取决于你怕什么。下面这几条是真实发生过的失手方式，不是假想敌：

| 威胁 | 为什么真实 |
|---|---|
| **托管方能读你的私有仓** | 私有仓对平台员工、对被盗账号都是可读的。"私有"是权限设置，不是加密 |
| **一次误设就公开了** | 私有仓改 public 只需一次点击；公开后 fork 出去的分支你删不掉 |
| **一把令牌通吃** | 一个带 `repo`+`workflow`+`gist` 的 PAT 被盗 = 整个账号被接管，攻击者还能改 CI 读 secrets |
| **静默失败** | cron 跑了三年，第一次真要恢复时才发现三个月前就 401 了。没有人验证过"成功" |
| **回滚攻击** | 攻击者不删你的备份，只把远端换成一个更旧的版本——你恢复出来的是"当时的样子"，缺的正是关键那几条 |
| **介质同归于尽** | 数据、私钥、备份脚本全在同一台机器同一个目录，机器没了就全没了 |

反过来说，**你不怕的东西别花力气防**：这不是区块链，不需要拜占庭容错，也不需要对抗拿到 root 的对手。

## 1. 四层，各管一件事

| 层 | 干什么 | 存哪 | 频率 | 谁管 |
|---|---|---|---|---|
| **L1 提交** | 把工作区改动落成本地 git 历史 | 库所在盘 | 每 30 分钟 | 定时器 |
| **L2 镜像** | 一份**不同物理盘**上的完整历史 | 另一块盘 | 随 L1 | 定时器 |
| **L3 加密快照** | 自包含、可离线恢复的整包 | 本地 + **两处异构远端** | 每天 | 定时器 |
| **L4 演练** | 证明 L3 真的能恢复 | 临时目录 | 每周 | 定时器 |

关键点：

- **L1 不是备份**。它在同一块盘上，盘坏就一起没。它的价值是"手滑删了还能找回"，不是灾备。
- **L2 必须换盘**。同一个根下的两个目录不叫两份副本。先在 `/proc/mdstat` 或 `lsblk` 上确认这两条路径落在不同设备上，再谈冗余。
- **L3 才是灾备**。它必须做到：拿到「一个 `.age` 文件 + 一把私钥」就能重建整个库，不依赖原机器上的任何东西。
- **L4 才是证据**。没跑过恢复演练的备份等于没有备份——你只是"有一堆文件"。

## 2. L3 怎么打包

### 2.1 一个整包，不要一堆小文件

按 atom 逐条加密是常见错误：**密文的个数、大小、增删节奏本身就是元数据**。168 个独立密文等于把"这个库里有多少条记忆、最近在记什么频率"直接告诉对手。

正确做法：`tar` 一整个目录 → `zstd` → **一个** age 密文。对象名用单调序号（`brain-000007.age`），日期只写在**加密后的** manifest 里——对象名不泄漏活动节奏。

```bash
tar --format=pax --sort=name --owner=0 --group=0 --numeric-owner -cf - . \
| zstd -19 -T0 \
| age -R recipients.txt -o "brain-$(printf '%06d' "$SEQ").age"
```

`--sort=name` + `--owner=0` 是为了**可复现**：同样的内容打出同样的字节，才能用 sha256 判断"这份是不是同一份"。

### 2.2 包里放什么

| 内容 | 为什么必须在包里 |
|---|---|
| `repo.bundle`（`git bundle create --all`） | 库的全部历史与分支，可 `git clone` 还原 |
| `manifest.json` | 本次快照的 `seq` / `created_at` / `git_head` / `atoms` / `tombstones` / `bundle_sha256` / **`prev_cipher_sha256`** |
| `state/tokens.json`、`state/audit.jsonl` | 没有它们，恢复出来的库没法接受老客户端的令牌 |
| `profiles/` | 人格/角色配置，不属于代码仓 |
| `RESTORE.md` | 半夜三点给未来的自己（或别人）看的操作步骤 |
| `restore.sh` | 一条命令做完恢复 + 自检，**演练就是跑它** |

### 2.3 校验：只存 sha256 是不够的

只把 `cipher_sha256` 写在旁边，攻击者换掉密文时**顺手把旁边那行也换掉**即可。所以：

1. **manifest 必须签名**：`ssh-keygen -Y sign -f backup-signing.key -n brain-backup manifest.json`（或 minisign）。验签公钥钉在**另一处**，不在备份仓里。
2. **manifest 必须串成链**：每份带 `prev_cipher_sha256`，指向上一份的密文哈希。这样"整段历史被替换成另一条自洽的链"就做不到，除非他能伪造签名。
3. **一行摘要落第二通道**：把最新的 `seq + sha256` 用邮件/聊天/短信发给未来的自己。这是带外锚点——攻击者能改对象存储，改不了你三天前的聊天记录。

演练时这三条都要检：验签、验链、对比锚点。任何一条缺了，这次"恢复"只能算"文件能解开"，不能算"数据没被动过"。

## 3. 密钥

- **age，不要 gpg**。`age` 是 X25519 + ChaCha20-Poly1305，每个文件独立随机密钥，密钥文件就是一个文本行，天然适合最小化保管。gpg 的信任模型在无人值守脚本里迟早被写成 `--trust-model always`——那等于把"验签"关掉，还留着 gpg 的心理安慰。
- **绝对不要**：`openssl enc -aes-256-cbc -pass ...`（无认证、弱 KDF、会复用 IV）、`zip -e`（ZipCrypto 已被破）、把口令放脚本里。
- **多收件人**：`age -r A -r B -R recipients.txt`，主密钥 + 恢复密钥各一份。主密钥日常用，恢复密钥离线封存——两者都不在备份里。
- **`age -p`（口令）只用于唯一那份灾难副本**：scrypt 口令可离线爆破、且口令无法轮换。它适合"写在纸上锁进抽屉"的场景，不适合每天跑的主路径。
- **私钥不与密文同机常驻**。这条最容易妥协，也是整套方案唯一的真单点：私钥和密文放同一台机器，等于没加密。最低限度是：私钥在离线介质上留两到三份，机器上那份只在跑备份时挂载/解密，用完就走。

---

## 4. 存哪：两处异构，永不同源

**两家，不同厂商，不同凭据，不同故障域。** 同一家的两个 bucket 不叫两份。

| 类型 | 要点 | 不能接受的实现 |
|---|---|---|
| 对象存储（S3 兼容） | 开**版本化** + **Object Lock（≥30 天）**；IAM 只给 `PutObject`，不给 `DeleteObject`/`PutBucketPolicy` | 用管理员密钥跑备份脚本 |
| 网盘（WebDAV / fuse 挂载） | 便宜、够大，适合放日备；注意它是**最终一致**的，写完必须读回校验 | 假定 `cp` 成功就等于写成功 |
| git 私有仓 | 只放**密文**；`.gitattributes` 标 `*.age binary`，避免 diff 泄漏大小变化 | **把明文压进去当"备份"**（等于把记忆交给托管方） |

关于 gist：**不要用**。gist 是 unlisted 不是 private——任何拿到 URL 的人都能读，没有访问日志、没有有效期、没有权限管理，而且它是 git 仓：别人 fork 之后你连删除都做不到。

写成功的判据不是退出码，是**读回来**：`sha256` 对得上才算写完。网盘挂载点尤其如此。

## 5. 保留策略

保留太多会让"找到对的那份"变难，保留太少则覆盖窗口不够。一个够用的默认：

| 层级 | 保留 | 说明 |
|---|---|---|
| 日备 | 14 份 | 覆盖"三天前就坏了但今天才发现" |
| 周备 | 8 份 | 约两个月 |
| 月备 | 12 份 | 一年 |
| 年备 | 3 份 | 三年 |

合计约 37 份。整包压缩后 400KB 量级 ⇒ **每年 75MB 左右**，任何介质都放得下。

**不要每小时全量**：一年 8760 份 × 400KB ≈ 3.5GB 的重复内容，而且没有一份比日备更有用。增量是另一件事，别混为一谈。

**删除权不要给备份脚本**：让脚本只有写权限，清理交给 bucket lifecycle 规则。脚本被投毒是最坏情况之一，它不该有能力删历史。

## 6. 成功必须是三证齐全

cron 报 `exit 0` 只说明 shell 没报错。真正的"备份成功"要同时满足：

1. **退出码 0**（脚本自己把每一步都做了 `set -euo pipefail`，且**不用管道去拿状态**——
   `git push | tee` 的退出码是 `tee` 的，推失败会被当成成功，这个坑很常见）；
2. **远端对象存在且哈希对得上**（读回来比，不是写完就算）；
3. **能恢复**：拉回最新密文 → 解密 → clone → 计数对得上 → `brain verify` 五项全过，并且这份是**链上最新的一份**（不是被回滚过的旧份）。

第 3 条不要放在备份脚本里（它太重、依赖网络），单独做成**每周演练**，写自己的状态文件。

### 告警链上不要放 LLM

用一个外部心跳服务（healthchecks.io 之类）：脚本开始时 ping `/start`，成功 ping 根路径，失败 ping `/fail`，服务端超过周期没收到就发邮件。**因为"备份挂了"和"替你监控的那个 agent 也挂了"经常是同一件事**——它们跑在同一台机器上。心跳 URL 放私有文件里，没有就静默跳过，不要把 URL 硬编码进仓库。

### 运行身份

- 用**专用的、无 sudo 的**用户跑备份（例：`backup`），只对它需要的目录有读写权。
- 用 **systemd timer**，不要用 agent 的 cron：`Persistent=true` 能补跑错过的窗口，`MemoryMax` 能防止它变成 OOM 凶手，`User=` 让权限边界写在单元里而不是靠脚本自觉。
- 加随机延迟（`RandomizedDelaySec`），避免所有机器同一秒去打同一个远端。

## 7. 恢复演练（这一节是全文的重点）

演练脚本要做的事，和真出事时你要做的事**完全一样**，否则它只是在验证一个不存在的流程：

```
1. 从远端（不是本地）克隆密文仓        ← 证明远端那份是活的
2. 验签 + 验 hash chain + 对比带外锚点  ← 证明没被替换/回滚
3. age 解密 → zstd 解压 → tar 解包
4. 跑包里的 restore.sh                 ← 演练同时测了"给人看的步骤"是否还正确
5. 独立断言：atoms 数量、git head、tombstones 数量与 manifest 一致
6. 独立跑 brain verify，期望五项全过
7. 抽查内容：brief 能渲染出摘要、随机抽 3 条 atom 正文非空
```

第 4 步最容易被忽略：**恢复文档本身会腐烂**。命令会变、行为会变（比如某些 git 版本要求 `bundle verify` 当前目录本身是仓），只有每次演练都真跑一遍 `restore.sh`，文档才配叫文档。

第 6 步有个必须知道的点：**`views/` 是派生目录、不进 git**，克隆出来是空的，所以恢复后**必须先 `brain reindex` 再 `verify`**，否则会得到一条 `views/.revision 与数据不一致` 的"失败"。这不是备份坏了，是流程少了一步。

### 手工恢复（没有脚本时）

```bash
age -d -i key.txt brain-000007.age | zstd -d | tar -xf - -C /tmp/restore
git clone /tmp/restore/repo.bundle /srv/brain
git -C /srv/brain fsck --no-progress
mkdir -p /srv/brain/state
install -m 600 /tmp/restore/state/tokens.json /srv/brain/state/tokens.json
BRAIN_ROOT=/srv/brain python3 /srv/brain/bin/brain reindex
BRAIN_ROOT=/srv/brain python3 /srv/brain/bin/brain verify     # 期望「五项全过」
BRAIN_ROOT=/srv/brain python3 /srv/brain/bin/brain serve --bind 127.0.0.1 --port 8790
```

恢复完顺手做一件事：`brain token revoke` 掉不再使用的令牌——恢复出来的 `tokens.json` 里有历史令牌。

## 8. 隐私分级：有些东西连密文都不该出去

加密保护的是"内容不被读"，保护不了"你在记什么、记多少"。而且一旦涉及**第三方的个人信息**（家人、同事、客户），加密不构成合法性基础——你没有权利把别人的处境拿去给第三方托管，哪怕托管方打不开。

一个够用的四级模型：

| 级别 | 例子 | 出网策略 |
|---|---|---|
| **L0 公开** | 公开的项目进度、技术笔记 | 随便 |
| **L1 内部** | 主机名、内网结构概要、配置偏好 | 加密后可出网 |
| **L2 私人** | 个人的计划、学习记录、健康习惯 | 加密后可出网，加密是必须的 |
| **L3 涉他人** | 家人的就业/健康、同事与公司的内情、未公开的商业信息 | **不出本机**（密文也不出） |
| **L4 凭据与定位** | 任何密钥/令牌的位置、门牌级地址、网络拓扑、MAC、内网 IP | **永不入库**，只记"去哪取" |

落地方式：

- atom 上加 `sensitivity` 标签，写入侧就 redact（先拦，别指望事后清理）；
- 备份脚本在打包前**按级别过滤**，L3/L4 留在本机那份快照里，远端只有 L0~L2；
- `brief` 渲染时**硬排除** L3/L4——摘要会进每一次对话上下文，它的暴露面比库本身大得多。

## 9. 凭据最小化

| 凭据 | 给什么 | 绝不给 |
|---|---|---|
| git 托管 PAT | `contents:write` 到**一个**数据仓（fine-grained token） | `workflow`（能改公开仓 CI 读 secrets）、`repo`（全账号） |
| 对象存储 | `PutObject`（+ `ListBucket`） | `DeleteObject`、`PutBucketPolicy`、`PutLifecycle` |
| 心跳服务 | 只能 ping 那几个 URL | 账号密码 |

另外两条硬规则：

- **备份凭据绝不与代码托管同账号**：代码仓被盗 = 备份仓一起没。
- **公开仓的 CI 里绝不出现备份凭据**：公开仓的 workflow 是所有人可读可改的（PR 就能改），任何注入其中的 secrets 都视为已泄漏。

## 10. 出了事：前 24 小时

```
T+0     断网取证：先别删任何东西，把当前状态留一份（镜像/快照/日志）
T+1h    判定类型：是托管方读到了明文？还是密文+私钥一起丢了？两者后果差一个数量级
T+2h    止血：吊销 PAT、改密码、开 2FA、撤掉 webhook 与 deploy key
T+4h    轮换：先撤凭据 → 再换备份口令/私钥 → 最后才是重新加密全量
        ⚠ 顺序颠倒会把自己锁在门外（旧钥已废、新份还没生成）
T+6h    告知：受影响的人先于公关稿
T+12h   隔离：可疑的本地副本单独放，不要就地"修好"
T+24h   复盘：写下"哪一步的假设错了"，写进库，别写进脑子
```

## 11. 红线清单

- 明文 atom **永不出网**（含"私有"仓、含加密盘挂载点）。
- 解密私钥**不同机常驻**、不进 git、不进 cron 的环境变量。
- 备份凭据**不给删除权**，不与代码托管同账号。
- 公开仓 CI **不含**任何备份凭据。
- **没有签名 manifest + hash chain 的备份，等于没有备份**——它能被替换，而你不会知道。
- **没跑过恢复演练的备份，等于没有备份**——你只是有一堆文件。
- 加密了但**没做隐私分级**的备份，等于把别人的隐私交给了第三方。

## 12. 常见反模式速查

| 反模式 | 为什么错 |
|---|---|
| 私有仓推明文当备份 | 托管方可读；一次误设 public 就永久泄漏（fork 删不掉） |
| 用 gist 当备份 | unlisted ≠ private，无权限、无审计、无有效期 |
| 一把 PAT 打通 repo+workflow+gist | 单点失守 = 账号全失 |
| 每小时全量 bundle | 一年 3.5GB 重复，且不比日备更有用 |
| per-atom 加密 | 密文条数与节奏本身泄漏元数据 |
| `openssl enc` / `zip -e` | 无认证加密 / 已被破的 ZipCrypto |
| `gpg --trust-model always` | 关掉信任判断，只剩心理安慰 |
| 只存 sha256 不签名 | 篡改者连校验值一起改 |
| `git push \| tee` 看退出码 | 拿到的是 `tee` 的状态，失败静默通过 |
| 备份跑在 agent 的 cron 里 | LLM 在环 = 多一个单点，且它和备份同机同命 |
